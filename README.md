# 料亭 川音 ― 予約につなげるLP（Web制作サンプル）

架空の料亭「川音（かわおと）」の予約用ランディングページです。ビジネス利用（接待・会食）の幹事や秘書が、**安心して電話・Web予約まで進めること**をゴールに、要件定義から設計・実装・検証までを行いました。

- **公開URL:** https://shoshoss.github.io/ryotei-sample/
- **制作期間:** 2026年10月（約2週間）
- **担当:** 要件定義、設計（仕様書の作成）、デザイン判断、実装の指示と検証、Git運用（すべて個人）

---

## このプロジェクトで示したいこと

コードを書く力そのものよりも、**仕様を決め、AIに実装させ、結果を検証して直す**という、基本設計から評価までの流れを一人で回せることを示すための作品です。

| 工程     | 行ったこと                                                                                      |
| -------- | ----------------------------------------------------------------------------------------------- |
| 要件定義 | ターゲット（ビジネス利用）とゴール（電話・Web予約）を決め、すべての判断の評価軸にした           |
| 基本設計 | 見た目の仕様（DESIGN.md）と中身の正本（CONTENT.md）を分けて作成。食い違ったときの優先順位も定義 |
| 詳細設計 | ブレイクポイントごとの振る舞い、コンポーネントごとのルール、アクセシビリティ基準を仕様化        |
| 実装     | Claude Code に仕様書を渡し、セクション単位で実装を指示                                          |
| 評価     | 複数の画面サイズで表示を確認し、仕様と違う点を洗い出して修正。必要に応じて仕様書自体を見直した  |

## 使用技術

| 分類                   | 内容                                                                                           |
| ---------------------- | ---------------------------------------------------------------------------------------------- |
| マークアップ・スタイル | HTML、CSS（CSS変数、Grid / Flexbox、`svh`、`env(safe-area-inset-bottom)`）                     |
| スクリプト             | JavaScript（メニューの開閉、FAQのアコーディオン、フォームの送信表示のみ。ライブラリ不使用）    |
| フォント               | Google Fonts（Shippori Mincho、1ウェイトのみ読み込み）、本文は端末標準のゴシック体             |
| 画像                   | WebP（2サイズを `srcset` で出し分け）、アイコンは自作のSVG（`currentColor` で色を継承）        |
| バージョン管理         | Git（機能ブランチ運用、Add / Update / Fix / Docs の接頭語でコミット）                          |
| AIツール               | Claude Code（実装）、Claude（仕様の相談・レビュー）、ChatGPT（デザインカンプと写真素材の生成） |
| 公開                   | GitHub Pages                                                                                   |

## 制作の流れ

1. **前提を決める** ― ターゲット、ゴール、店舗の設定、価格を決定。価格は地域の相場を調べ、自身の料亭での勤務経験（5年）と照らして設定
2. **仕様書を作る** ― 参考サイトの配色や余白を分析し、DESIGN.md と CONTENT.md を作成。作成後に第三者視点で見直し、法令（税込の総額表示）や、架空の電話番号の扱いなどの漏れを修正
3. **デザインカンプを作る** ― ファーストビューを3案作って比較し、方向性を決めてから1セクションずつ作成
4. **素材を用意する** ― 写真を文字なしで1枚ずつ生成し、比率の切り抜きとWebP変換。アイコンはSVGで作成
5. **実装と検証** ― セクション単位で実装を指示し、画面サイズごとに確認。問題があれば仕様書から直す

## 判断した点

実装中に見つけた問題と、その判断の例です。

| 課題                                                   | 判断                                                                                 | 理由                                                                                          |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 低いスマホ画面で、キャッチコピーとサブコピーが重なった | ファーストビューを「価格まで1画面に収める」構成から、「写真だけで1画面」の構成に変更 | 写真の格式を活かし、重なりを根本から解消するため。予約導線は画面下の固定バーで常に確保        |
| 本文がゴシック体中心で、料亭らしさが出なかった         | 「短い文や見せる文字は明朝体、長い文章と操作部分はゴシック体」に仕様を変更           | 雰囲気と読みやすさの両立。Webフォントは1書体1ウェイトに絞り、表示速度を維持                   |
| 電話ボタンの色が暗く重かった                           | 藍を `#1F3B4D` から `#2E5A78` に変更                                                 | 墨（暖色系の黒）の補色にあたる青系をアクセントに選定。白文字とのコントラスト比 約7.4:1 を確認 |
| 固定バーがスマホで3〜4行になり、本文を隠していた       | スマホでは2行以内に収め、アイコンを外す                                              | 予約しやすさのための部品が、読みやすさを損ねないようにするため                                |
| 室料・サービス料が別で、総額が分からなかった           | 税込の総額表示に統一し、「お一人様あたりの目安」の計算例を掲載                       | 法人の幹事が事前に予算を通せるようにするため                                                  |

## 見やすさ・使いやすさへの配慮

見た目を整えるだけでなく、予約情報を確認しやすく、さまざまな環境で操作できることを意識して実装しました。

- **動きを減らす設定に対応**：OSで「動きを減らす」設定をしている場合、ファーストビューのフェードインやボタンなどの変化を止め、動きが苦手な人にも見やすくした
- **キーボード操作に対応**：マウスを使わなくても、現在選択しているリンクやボタンが分かるようにした
- **音声読み上げに配慮**：見出し・メニュー・本文など、HTMLの役割に合った要素を使い、メニューやFAQの開閉状態も伝わるようにした
- **画像の説明文を設定**：内容を伝える写真には、何が写っているか分かる説明文を設定した
- **スマートフォンの操作性に配慮**：入力欄を16px以上にし、iPhoneでの自動ズームを防止。画面下部の固定予約バーが端末の表示領域と重ならないようにした

## 検証したこと

- 画面サイズ：375×667、375×844、768×1024、1440×900
- 文字と背景のコントラスト比（WCAGの 4.5:1 以上）
- iPhoneの画面下の余白（safe-area）と、固定バーの重なり
- キーボード操作時のフォーカス表示、`prefers-reduced-motion` への対応
- 入力欄の文字サイズ（16px以上。iPhoneで画面が自動拡大されないようにする）
- iPhone（Safari）の実機での表示。MacにつないだWebインスペクタで、ページの幅が画面の幅を超えていないかを計測

## AIと自分の役割分担

| 担当        | 内容                                                                   |
| ----------- | ---------------------------------------------------------------------- |
| 自分        | 要件、仕様書の内容、デザインの採否、AIへの指示、表示の確認と修正の判断 |
| Claude Code | 仕様書に沿ったHTML・CSS・JavaScriptの実装、画面サイズごとの計測        |
| Claude      | 仕様や判断のレビュー、指示文の下書き                                   |
| ChatGPT     | デザインカンプと写真素材の画像生成                                     |

AIの出力はそのまま採用せず、仕様書と照らして確認しました。たとえば、AIが「問題なし」と報告した箇所でも、計測値を見て固定バーとの4pxの重なりを見つけ、修正させています。

## 公開後の改善

公開後に見つけた不具合も、イシューに記録し、作業用のブランチで直して、プルリクエスト（PR）で取り込んでいます。

### 例：スマホで横スクロールが出る不具合（[#5](https://github.com/shoshoss/ryotei-sample/issues/5) → [PR #7](https://github.com/shoshoss/ryotei-sample/pull/7)）

| 段階 | 行ったこと |
|---|---|
| 発見 | 公開後、iPhoneで横スクロールが出ることに気づき、イシューに記録 |
| 1回目の修正 | タブレット用のメニューパネルが原因と考えて修正したが、その指定は768px以上でしか効かず、スマホの原因ではなかった |
| 原因の特定 | 確認用のブラウザでは再現しなかったため、iPhoneをMacにつなぎ、SafariのWebインスペクタで画面幅を超える要素を調べた。予約フォームの日付の入力欄が、iPhoneのSafariで幅の指定を無視して広がっていたことを特定 |
| 修正の絞り込み | 固定バーにも予防的な修正を入れたが、原因の分からない変更は残さない方針で外し、日付の入力欄の修正だけで収まることを実機で確認 |
| 取り込み | 差分を自分で確認してコミットし、原因・変更内容・確認したことをPRに記録してマージ |

### この経験から決めたルール

- 見た目の不具合は、確認用のブラウザだけで判断せず、実機で確かめる
- 原因を特定してから直す。`overflow-x: hidden` などで隠すだけの対応や、原因の分からない予防的な修正は入れない
- AIの「問題なし」という報告も、実機や計測値で確かめてから取り込む

### 開発の進め方

- GitHub Flow（main と作業用ブランチ）で開発。ブランチ名は `feature/`・`fix/`・`docs/` で用途を分ける
- コミットは Add / Update / Fix / Docs の接頭語を付け、ドキュメントとコードの変更を分ける
- main はルールセットで保護（PR必須、強制pushと削除を禁止）。マージ後のブランチは自動で削除
